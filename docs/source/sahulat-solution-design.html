Working name: Sahulat (سہولت) — placeholder, rename freely

One WhatsApp number that can answer anything and do anything a business allows.

A business plugs in two things — its documents and its APIs. Sahulat turns them into an agent that lives on WhatsApp (text, voice notes, and eventually calls), recognises the customer by phone number, verifies them when it matters, and performs real operations on their behalf. Strictly inside that business's domain, nothing else.

The concept, restated

Every business already has a WhatsApp number people message. Today that number is either ignored, answered by a human, or wired to a menu bot that can only follow a script. Sahulat replaces the script with an agent that understands the request, looks things up in the business's own knowledge, calls the business's own systems, and completes the task — all in the same chat window the customer already uses.

The business doesn't build a bot. It describes itself: here are our documents, here are our APIs, here is how you verify our customers, here is what the agent may and may not do. Sahulat does the rest.

The product is a gateway, not a chatbot. Its job is to sit between a messaging channel and a business's systems, and to make the bridge safe, grounded, and auditable. Everything else — sales, support, service desk, ops — is a configuration of that gateway.

Four primitives

Every capability in the product reduces to one of four things a business configures. Keeping the model this small is what makes "any business, any purpose" achievable without building a new product per vertical.

Channel

Where conversations arrive. WhatsApp Cloud API is channel one: text, images, documents, voice notes, interactive buttons, templates. The gateway normalises every channel into one message envelope so the agent never knows or cares which channel it's on.

Knowledge

What the agent may say. PDFs, DOCX, spreadsheets, web pages, product catalogs, policy docs, FAQ exports. Ingested, chunked, embedded, versioned. The agent answers only from this corpus plus what the APIs return — never from the model's general memory.

Actions

What the agent may do. The business publishes an OpenAPI manifest (or an MCP server) annotated with risk levels. Read actions run freely; write actions need the right identity tier and, for high-risk ones, an explicit in-chat confirmation.

Identity

Who the agent is talking to. The phone number is the principal. The business supplies a lookup (is this number a customer?) and a step-up method (OTP, PIN, or their own auth API). Identity tier gates which actions unlock.

System architecture

Five planes. Channels on the left, business systems on the right, the orchestrator in the middle. The control plane is the business-facing product; the data plane is what runs conversations.

Design decisions that matter

  • Channel gateway is thin and dumb. It knows WhatsApp's quirks — 24-hour service window, template approval, media URL expiry, interactive message types — and nothing about the business. Adding a channel is adding one adapter.
  • The orchestrator owns policy, not the model. Which tools exist for this user at this identity tier is decided in code before the LLM sees anything. The model can only ask for tools it was given.
  • Knowledge and actions are both "tools". Retrieval is just a read tool over the document corpus. This keeps the planner simple: every turn is "which tools, in what order, then reply".
  • Model layer is swappable per tenant. A SaaS tenant may route to a hosted frontier model; a sovereign tenant routes to vLLM on their own GPUs. Same orchestrator, different config.
  • Everything writes to the audit log — inbound message, retrieved chunks, tool calls with arguments and results, model prompts and outputs, handoffs. Regulated clients will ask for this on day one.

A conversation, end to end

A bank customer sends a voice note in Urdu: "block my card, I lost it". The whole thing takes under ten seconds and never leaves WhatsApp.

Turn loop, generalised

  1. Ingest — webhook → verify signature → normalise → fetch media → enqueue.
  2. Resolve — tenant from WABA phone id; session from (tenant, customer number); identity tier from cached lookup.
  3. Understand — ASR for audio, vision for images, language detection. Guardrails scan for injection and out-of-domain intent.
  4. Plan — the LLM sees: system prompt (persona + domain fence), session memory, retrieved knowledge, and only the tools permitted for this tier. It emits a plan: reply, or tool calls, or escalate.
  5. Gate — each tool call is checked against policy: tier sufficient? confirmation required? rate limit ok? If step-up needed, pause plan, run OTP sub-flow, resume.
  6. Execute — call the business API / MCP tool. Results go back to the model for the final reply. All of it hits the audit log.
  7. Reply — text, or TTS audio if the customer spoke; interactive buttons where the next step is a choice; template message if outside the 24h window.

Identity & trust model

The phone number is the principal. That is the whole reason WhatsApp beats a website: the customer is already half-authenticated before they type a word. The product formalises this into tiers.

TierHow it's reachedWhat unlocksLifetime
AnonymousAny number messages the businessPublic knowledge: hours, products, policies, how-to. No customer data.Session
KnownBusiness's lookup API matches the number to a customer recordLow-risk personal reads: order status, ticket status, next appointment. Business decides.Cached, refreshed per session
VerifiedStep-up: OTP to the same number, PIN, or business's own auth API (e.g. app push approval)Sensitive reads (balances, statements) and write actions (block card, change address, place order, pay bill).Configurable, default 15 min
PrivilegedStaff number allow-listed + step-up; or SSO via linkInternal tools: ticket assignment, inventory update, approvals, ops runbooks. Same agent, different scope.Configurable

New-customer registration is the same mechanism in reverse: the business exposes a register action; the agent collects fields conversationally (name, CNIC, email — whatever the manifest says), the number is verified by the fact they're messaging from it, and the record is created.

The agent never holds credentials. Step-up is a business-owned flow; Sahulat brokers it and stores only a short-lived tier token. For banks this is the difference between "pilotable" and "instant no".

Business onboarding

The promise to a business is "describe yourself, don't build a bot". Onboarding is the product; if this takes more than a day for a mid-size company the positioning fails.

Prebuilt connectors shorten step 3 for common systems: Shopify / WooCommerce, Zoho, HubSpot, Odoo, Freshdesk, Jira Service Management, Google Calendar, and — for your market — templates for core-banking gateways, bill-payment aggregators, and a generic "Excel-as-database" connector for businesses whose "system" is a spreadsheet.

Connector spec

A tenant's integration is a folder, not code. Three files plus optional webhooks.

Action annotation example

paths:
  /cards/{card_id}/block:
    post:
      operationId: block_card
      summary: Block a debit or credit card
      x-agent:
        description: Use when the customer reports a lost, stolen, or compromised card.
        risk: high
        required_tier: verified
        confirm: true              # agent must restate and get explicit yes
        idempotency: card_id       # safe to retry
        audit_fields: [card_id, reason]
        followups: [request_replacement_card]
  /orders/{order_id}:
    get:
      operationId: get_order_status
      x-agent:
        risk: low
        required_tier: known
        ownership_check: customer_id   # result must belong to the caller

The ownership_check field is what stops a known customer from reading someone else's order by guessing an id: the orchestrator verifies the returned record's owner matches the session principal before the model sees it.

Same codebase, two deployment shapes. The SaaS shape is for SMBs and retailers who want to be live in an afternoon. The sovereign shape is for institutions that cannot let customer conversations or documents leave their perimeter — and it's the one no global competitor offers in your market.

Guardrails & safety

"Strictly this business only" is enforced in layers, not by a sentence in the prompt.

Domain fence

A lightweight classifier (small model or embedding similarity to the tenant corpus) scores each message for in-domain. Out-of-domain gets a fixed, polite refusal in the tenant's voice. The main LLM never sees it.

Tool exposure by tier

The model only receives tool definitions permitted for the current tier. It cannot request a tool it doesn't know exists. Escalation of tier is orchestrator state, never model output.

Prompt-injection defence

Retrieved chunks and API results are wrapped as data with explicit boundaries. Instruction-like text inside documents or tool results is flagged and stripped. Customer-uploaded files are never treated as instructions.

Ownership & scope checks

Every read result is checked against the session principal before the model sees it. Write actions carry idempotency keys and are logged with arguments, actor tier, and confirmation transcript.

PII handling

Configurable redaction (CNIC, card numbers, addresses) in logs and in model context. Images of ID documents are processed by the vision model and discarded per policy; extracted fields go straight to the business action.

Human in the loop

Handoff on low confidence, sentiment threshold, explicit request, or high-risk action if the tenant chooses supervisor mode. The human sees the full transcript, tool trail, and can hand back to the AI.

Commercial model

SaaS

  • Starter: docs-only FAQ agent, one number, capped conversations/month
  • Growth: actions + connectors, voice notes, analytics, human inbox seats
  • Scale: multiple numbers, prebuilt connector packs, priority models, SLA
  • Usage: per-conversation on top, pass-through of Meta's per-conversation fees + LLM cost with margin

Sovereign

  • Implementation project: deployment, connector build, Urdu ASR tuning, evals
  • Annual licence per instance (sized by conversations or channels)
  • Support & updates SLA; optional managed operations from your team
  • Connector packs (banking, government, telecom) as add-on licences

Sovereign deals fund the SaaS build: a single bank licence covers a year of SaaS engineering. Price sovereign on value (call-centre minutes displaced), not on cost.

Risks & open questions

  • Meta policy on AI agents and calling. Confirm current Business Messaging and Calling API terms for automated voice, and what "AI-generated response" disclosure is required. This gates phase 3 and should be verified before it's promised to any client.
  • Per-conversation pricing in PKR. Meta's rates change; model the unit economics for a high-volume bank before quoting.
  • Urdu ASR quality. Off-the-shelf models are weak on code-switched, noisy voice notes. Treat as an R&D track with a data-collection plan from day one, and set expectations with the first client.
  • Regulatory. SBP outsourcing and data-localisation rules for banks; PTA requirements; the Personal Data Protection Bill's status. Sovereign deployment is the answer, but the paperwork still needs doing.
  • Open-weight model tool-calling reliability. Sovereign tenants can't use frontier hosted models. Benchmark candidate models on structured tool use and refusals early; this decides what "sovereign" can honestly promise.
  • Scope discipline. The largest risk is internal: building ERP/CRM/DevOps features before the gateway is proven. The table in §10 is a roadmap of connector packs, not a feature list for v1.
  • Competition. Global SaaS players (Ainisa, YourGPT, Yellow.ai, charles) and local integrators (Convo, Intellicon, TekkPak) exist. None sells a sovereign, on-prem, Urdu-voice-first agent gateway to regulated Pakistani institutions. That is the position to hold; the SaaS tier follows.
